# Client demo — walkthrough

About 20 minutes, all of it on the laptop. Everything below works on either set
of data: the invented one (`platform.ps1 demo-data`, no customer's details on
the screen) or the shop's own (`platform.ps1 import-legacy`).

## Before the meeting (10 minutes, once)

1. Double-click **`START.cmd`**. Wait for *Ready* and the browser to open.
2. Put the data in — **one** of:

   ```powershell
   powershell -ExecutionPolicy Bypass -File scripts\platform.ps1 demo-data
   ```

   Invented customers, orders and parcels over the last fortnight, at every
   stage: waiting to be picked, with J&T, delivered, returned (type `DEMO`).
   Nothing real on the screen, and it can be re-run between rehearsals.

   ```powershell
   powershell -ExecutionPolicy Bypass -File scripts\platform.ps1 import-legacy
   ```

   The shop's own data: the warehouse backup and the J&T export, linked to each
   other (type `IMPORT`). Use this to show the client their own orders.
3. Check: `powershell -ExecutionPolicy Bypass -File scripts\platform.ps1 status` — every service *healthy*.
4. Two browser windows side by side: **A** the warehouse, **B** the courier
   portal. Close any old tabs on `localhost:3000` / `:8000`.

Accounts: `admin` / `admin123` (everything), `linked` / `linked123` (merchant).

Every time on every screen is Malaysia time (`APP_TIMEZONE` in `.env`), so on a
laptop set to Pakistan time the clocks read three hours ahead of the taskbar.

---

## 1. One platform, one login  (2 min)

*"Two systems became one: one address, one database, one login."*

1. Window A → <http://localhost:5080> → the Inaaya login page → **admin / admin123**.
2. The **warehouse** opens straight away — staff start where they work.
   Point out the masthead: the shop's own wordmark, the same one as the portal.
3. Sidebar → **Shipping portal ↗**. The courier portal opens **without asking
   for a password** — the same session, the same account, the same look.
   Its homepage carries **Across the platform**: live warehouse numbers
   (orders to pick, parcels with J&T, delivered, COD to collect, garments in
   stock) on the courier's side of the house.
4. Back in window A, or from the portal's own menu, **Courier admin** lists
   every parcel with its latest scan.

## 2. The warehouse  (4 min)

1. **Overview** — stock value, orders to pick, and the **J&T** row: with J&T,
   delivered, COD to collect.
2. **Products** — the catalogue with photos. Optional: *Search by photo* with a
   product picture.
3. **Orders** — the **J&T parcel** column: every order that went out carries its
   real tracking number, and the *Delivered* tab is filled by the courier's own
   scans, not by anybody typing.
4. Open a **delivered** order → **J&T courier**: tracking number, sortation and
   route code, freight, cash on delivery, the parcel's journey, **Print waybill**
   (the 3-copy J&T label as a PDF) and **Tracking page**.

## 3. Book J&T from a warehouse order  (5 min)

*"Before: pick in the warehouse, then type the order again into the J&T portal.
Now: one click."*

1. **Orders → New order**
   * Customer: `Demo Customer`, phone `012-345 6789`, city `Petaling Jaya`,
     postcode `47810`, address `No. 12, Jalan PJU 5/1, Kota Damansara`,
     payment **Cash on delivery**.
   * **+ Add a garment** → search `chiffon` → pick a **dropship** colour of
     *Heavy Chiffon Suit with Plazo & Dupatta*, so there is nothing to scan.
     **Place order**.
2. On the order: **Send it out** → confirm → *Shipped*.
3. **Send with J&T courier** (mobile, postcode and address are filled in from the
   order) → weight `0.8` → **Book J&T courier**.
   The tracking number, sortation code, freight and COD amount appear immediately.
4. **Print waybill** → the real J&T 3-copy label, generated by the courier module.

(With stock products the same happens after the last garment is scanned — on the
C72 handheld or in the dashboard's scan box.)

## 4. The courier's tracking flows back  (3 min)

*"And the warehouse finally learns when a parcel arrives."*

1. On the order → **Open in courier admin** (or window B → <http://localhost:5080/admin>
   and search the tracking number). The drawer shows the banner
   **Warehouse order SO-… · shipped** — the courier knows which warehouse order it is.
2. **Change the status** → *Picked Up* → Save; then *Delivered* → Save.
3. Back to the warehouse (the banner's **Open in warehouse ↗**, or refresh window A):
   the J&T panel says *Delivered* at once and the order itself is **Delivered**
   within ~20 seconds; the journey lists the scans, *Cash on delivery* reads
   *collected by J&T*, and *Overview* counts it as delivered.
4. The customer's view: <http://localhost:5080/tracking> → paste the tracking number.

Optional: mark a parcel **Returned** in the courier admin → the warehouse
**Returns** page gets a new return *"Parcel … returned by J&T"*, waiting for the
garments to be scanned at the desk. (Returns open for orders that have gone out,
so use one of the shipped orders or a demo order you just booked.)

## 5. Accounts, security and the phone  (3 min)

1. Warehouse → **Users** (or courier admin → Users): the **same list** — one
   account table for the platform, with roles *admin*, *operator*, *merchant*.
2. The account, top right of either module, opens the same little menu: the other
   module, this one, the profile, and **Sign out**. Sign out → both modules are
   signed out at once: the other one's next click goes to the login page.
3. Sign in as **linked / linked123** → the merchant sees the courier portal only;
   the Warehouse link and the warehouse numbers are not there, and `/warehouse/`
   politely refuses.
4. Narrow the browser window (or open it on a phone): the menu folds into the
   button at the top left, the tables keep their own scroll, and both modules
   stay usable — the same on a packing bench tablet as on the office laptop.

## 6. How it is built  (3 min)

Show [ARCHITECTURE.md](ARCHITECTURE.md):

* **One PostgreSQL database** with a schema per module (`warehouse`, `courier`)
  and a shared `core` for accounts, sessions and the audit log; each service has
  its own database role and cannot write the other's tables.
* **Gateway on port 5080** — the port the handhelds already look for, so every
  device in the field keeps working with no update.
* **Single sign-on** with revocable sessions, ended everywhere at once; CSRF and
  brute-force protection; audit log of logins, account changes and bookings.
* **One design** across both modules: the shop's wordmark, typeface and controls,
  and the same clock (Malaysia time) on every screen.
* **Docker Compose**: health-checked services, non-root containers, JSON logs with
  one request id across services; `platform.ps1 backup | restore`.
* **Tests**: 337 warehouse checks and 504 courier tests pass on the shared
  database, plus 49 end-to-end checks across the modules; CI pipeline included.

### If something goes wrong during the demo

| Symptom | Quick fix |
|---|---|
| Page does not load | `scripts\platform.ps1 status`; `docker compose restart gateway` |
| "Your session has ended" | sign in again (sessions last 12 h on the warehouse, 7 days on the portal) |
| Booking refuses the postcode, phone or address | J&T Malaysia needs a 5-digit postcode, a mobile number and an address — correct them on the booking form |
| Status did not change in the warehouse | wait 20 s (sync interval) and refresh |
| A rehearsal's orders are showing | `scripts\platform.ps1 demo-data` (type `DEMO`) puts a clean set back |
